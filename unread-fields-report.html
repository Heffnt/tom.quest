What a reader would show for the eleven unread fields

Four cases, measured against the running deployment on 2026-09-01. Nothing in the repository was changed.

What this is

tom.quest is a personal web application. Its data lives in Convex, a hosted service that both stores the rows and runs the server functions that write them. The shape of every table is declared in one file, convex/schema.ts; Convex checks each write against that declaration, so a declared field costs a line of schema, a validator, and a write on every update, whether or not anything reads it back.

Four separate reviews found the same defect in four places: a value is computed, sent, checked and stored, and then no screen ever draws it. Eleven fields across four tables. The batch these belong to asks one question of each of them — draw it on a screen, or delete it together with the code that writes it — and that question cannot be answered from the field names, because the whole of it is what the screen would say. This report is that measurement.

Three terms used throughout, defined once. A component is one file of front-end code that produces one region of the page. A subscription is the front end asking Convex for a value and being re-sent it whenever it changes; in this codebase that is the call useQuery(...), and a component that already subscribes to a row already has every field of that row in the browser, whether it draws them or not. A cron is a server function Convex runs on a fixed timer with no user involved.

How this was measured, and what could not be measured

Four of the eleven values were read out of the live deployment. The Convex query serverHealth.get performs no identity check, so an unauthenticated request to the deployment's public URL returns the Turing health row; that is the real reading quoted in case 1 below. Everything else is behind an identity check — forge.listMine, claudeSessions.getDaemonHealth and gpuPool.status all require your account, and the deployment refused each of them for this session.

The Turing cluster's own API answers GET /health with {"status":"ok"} right now, but rejected the API key present in this session's environment on GET /jobs and on the Forge endpoints, so no live training run could be read either. Where a real value was unavailable the report says so and gives the value's exact provenance in code instead of inventing one.

One fact found while measuring, outside this batch's scope and stated once: convex/serverHealth.ts:8-16 declares get with no identity check, so anyone who knows the deployment URL — which is public by construction, it is compiled into the browser bundle — can read whether the Turing cluster is up and when it was last reached. That is how the reading below was taken.

Case 1 — serverHealth.lastSuccessAt

The real value, right now

The row the deployment returned today, verbatim: {"serverName":"turing","reachable":true,"lastChecked":1788288336731,"lastSuccessAt":1788288336731}. The two timestamps are identical, and that is the central fact about this field. A cron probes the cluster every 30 seconds (convex/crons.ts). Every probe that succeeds writes the same instant into both lastChecked and lastSuccessAt, so while Turing is up the field is an exact duplicate of one already being read. It carries information only while reachable is false — and then it is the only value in the system that says since when.

The line a screen would gain

There is no user-facing screen to add it to. The single reader of the Turing health row is the hook app/lib/hooks/use-server.ts, whose status object exposes exactly three values — connected, fresh, error — and whose only consumer in the entire application is the Tom-only diagnostic panel, app/components/debug-panel.tsx:80-86. The Turing dashboard page itself (app/turing/turing-client.tsx) never renders cluster health at all; it discovers unreachability by its own requests failing.

So the honest answer is two different answers.

The repair, which changes an existing surface: the diagnostic panel registers a turing block of labelled values that the panel's copy button emits as text. Adding one entry there displaces nothing.

turing: connected true · fresh true · error null
turing: connected false · fresh true · last reachable 14m ago · error "health returned 502"

The new surface, which is a larger decision than this batch contains: a health line in the Turing dashboard header (app/turing/turing-client.tsx:23-30), reading Turing unreachable — last reachable 14 minutes ago and drawn only when reachable is false. That requires widening ServerStatus in the hook by one field, because the hook currently discards the whole row and hands on only its three derived values.

Absence and staleness

The field is durable and honest. The write at convex/serverHealth.ts:35 is lastSuccessAt: args.lastSuccessAt ?? existing.lastSuccessAt — a failed probe passes nothing and the stored value is carried forward unchanged, which is exactly what a "last reachable at" needs. It is absent only for a server that has never once been reached since the row was created.

Cost of deleting

Four lines, no coordination with anything outside Convex: convex/schema.ts:30 (the declaration), convex/serverHealth.ts:23 (the argument validator), :35 (the carry-forward), :75 (the one place a value is passed, on a successful probe). No test asserts on it.

Recommendation: render it in the diagnostic panel, as an age, and only when the cluster is unreachable. The reason is that the field is free when things are working — it duplicates lastChecked — and is the only answer to "how long has this been down" when they are not, and four lines is not a cost worth paying to discard that.

Case 2 — claudeDaemonHealth.version and .activeAccount

The real values, and their provenance

The live row is behind your identity and could not be read. Both values are fully determined by code that is in this checkout, so their exact form is known.

version is the literal string session-host/${VERSION} assembled at worker/session-host/session-host.mjs:272, where VERSION is the constant "0.2.0" at line 36 of the same file. The value stored today is therefore session-host/0.2.0, and it changes only when that constant is edited and the daemon restarted.

activeAccount is the last path segment of the symbolic link /root/.claude-accounts/active, read at session-host.mjs:60-66 and left undefined if the link is missing. The automatic account switch at :84-90 refuses to act unless the value is exactly gmail or wpi, so those two strings and undefined are the whole range.

The line a screen would gain

Both values are already in the browser. claudeSessions.getDaemonHealth returns the whole row, and two components subscribe to it: app/sessions/sessions-client.tsx:29 and app/sessions/components/session-list.tsx:63. Drawing them is a front-end change only — no schema, no server function, no deploy of the worker.

The right home is the autonomous-fleet row in session-list.tsx:113-131, which already carries the switch and the box's load on one wrapping line:

auto off load 0.42/16 · 22.1 GB free · 3 sessions edit
auto off load 0.42/16 · 22.1 GB free · 3 sessions · gmail · session-host/0.2.0 edit

Nothing is displaced. That line is a wrapping flex row and the edit button is pushed to the far right by ml-auto, so two more items extend it or wrap it and move nothing else.

The stale-daemon banner at sessions-client.tsx:66-86 is the wrong home, and this is worth stating because the field list makes it look like the obvious one. That banner renders only when the daemon has gone quiet for 90 seconds or a write was rejected. Which account the box is signed in to is a fact you want while the fleet is working — it is what decides which usage limit is being consumed — and the banner is absent exactly then.

Absence and staleness

version is never absent: convex/http.ts:1248-1250 rejects a heartbeat without it with a 400 before the mutation runs. activeAccount is optional and is undefined whenever the symbolic link is missing or the box was not set up with the two-account arrangement. Neither can go stale relative to the other: the heartbeat write at convex/claudeSessions.ts:777-784 always carries both, throttled to at most one write per 10 seconds.

Cost of deleting

The two fields are very different on this side, and the difference is the argument.

activeAccount costs about nine lines across five files: convex/schema.ts:1088, convex/claudeSessions.ts:745 (validator), :781 and :791 (the two writes), convex/http.ts:1257-1258, session-host.mjs:274 and the function at :60-66, and the assertion at convex/claudeSessions.test.ts:219 and :229. It deletes cleanly.

version does not delete cleanly. The check at convex/http.ts:1248-1250 makes it required — a heartbeat without it is answered 400 and the daemon's report is dropped. Removing the field means relaxing that check and deploying the two sides in order, Convex first and the worker second, so that no heartbeat is ever rejected mid-change. That is more work than drawing it.

Recommendation: render both, on the fleet row. The reason is that the entire cost is one clause of front-end code in one file, since both values are already subscribed to and in the browser, and the delete side costs a coordinated two-sided deploy for one of them.

Case 3 — the five GPU-pool counters

They are per-pass, and they are almost always zero

The task asked whether these are cumulative or per-cycle. They are per-cycle, without exception. allocated, cancelled, staleCancelled and adopted are each declared as a fresh zero inside the per-pool loop on every run (convex/gpuPool.ts:489, :510, :605-606), and orphansCancelled is the length of one pass's orphan list (:463). The status document is a single row replaced whole every pass (writeStatus, :352-368), and the cron runs every 60 seconds. Each counter therefore describes the last 60 seconds and is destroyed by the next pass.

Their magnitudes make this sharper. allocated is 0 or 1 and never more, because a pass allocates at most one job per pool (:611-618). cancelled is nonzero only on a pass that found the pool above its desired count, which happens after you lower that count. staleCancelled and adopted are nonzero only on the one or two passes following a configuration edit that changed the pool's fingerprint. In steady state every one of the five reads zero, so a rendered line would read allocated 0 · cancelled 0 · stale 0 · adopted 0 on virtually every pass you ever look at.

The staleness problem, which is the decisive fact here

When the reconciler cannot reach the Turing API it skips the cycle and preserves the previous pass's per-pool entries verbatim — pools: prev?.pools ?? [] at convex/gpuPool.ts:384, :407 and :419 — while writing a fresh ranAt. The counters are inside those preserved entries.

pass at 10:00 allocates one job → allocated: 1
↓
pass at 10:01 cannot reach the API → row rewritten with ranAt = 10:01 and allocated: 1 copied forward
↓
panel draws Last reconcile: 4s ago · allocated 1 — for the whole outage, about an allocation that happened before it

Drawn as they stand, next to the "Last reconcile" age that already exists at pool-panel.tsx:229-233, these counters would state something false during exactly the situation you would be looking at the panel to understand. Any render has to be conditioned on jobsFetchOk being true.

The line a screen would gain

The four per-pool counters belong on the per-pool row at app/turing/components/pool-panel.tsx:262-273; orphansCancelled is a run-level number, not a per-pool one, and belongs next to the reconcile age at :229-233.

A100 1 / 1 running (+0 starting) always python worker.py
A100 1 / 1 running (+0 starting) · allocated 1 always python worker.py

Nothing is displaced — that row also wraps. The counters should be drawn only when nonzero, otherwise the line acquires four permanent zeros.

Cost of deleting, which is higher than the field count suggests

The declarations and writes are eleven lines: convex/schema.ts:83 and :90-93, convex/gpuPool.ts:327-328, :343-344, :357, and the values pushed at :648-651 and :670-671, plus the local type in pool-panel.tsx:32-35 and :49.

The real cost is in the tests. convex/gpuPool.test.ts asserts on these counters as the observable proof that three reconciler behaviours happened at all: expect(st?.pools[0].adopted).toBe(1) at :191 is the only assertion that adoption of an unknown live job occurred, staleCancelled at :212 is the only assertion that a job from a superseded configuration was drained, and orphansCancelled at :273 is the only assertion that orphan cleanup ran. Deleting the fields deletes those three tests' subject. The behaviours could be re-asserted against the gpuPoolAllocation rows instead, but that is a test rewrite, not a field removal.

Recommendation: keep the fields and render them conditionally — only the nonzero ones, and only on a pass where jobsFetchOk is true. The reason is that the fields are load-bearing for three regression tests regardless of the screen, so the delete option is not the cheap one it appears to be, and a conditional render is the only form of them that is never false.

Case 4 — the four Forge adapter fields

The two things the task said to check rather than assume

Both checked, and both change the answer within this case.

isAdapter is derivable from adapterPath. The cluster API refuses to serve a run whose result claims is_adapter without an adapter_path, and refuses a non-adapter run without a model_dir (turing-api/forge.py:336-339). For every run that can be served, "is an adapter" and "has an adapter path" are the same statement, and the stored boolean carries nothing the path does not.

modelDir is not what the serve job uses. Starting a server sends only the run identifier — startServe.trigger({ run_id: job.runId }) at app/forge/components/job-list.tsx:107. The API then reads base_model, is_adapter, adapter_path and model_dir out of that run's own result.json on the cluster (forge.py:324-339) and passes them into the batch job's environment (:349-353). The Convex copies are never consulted. Deleting all four would not affect serving in any way.

A third thing worth naming: epoch has no writer in this repository. result.json is produced by python -m boolean_backdoor.forge_launch, invoked at turing-api/forge_scripts/forge_train.sbatch:52, which lives in the CMT repository and is not in this checkout. The two declarations here disagree about it — app/forge/types.ts:41 says epoch: number, required and non-null, while convex/forge.ts:79 accepts a number or null — and nothing in this repository can settle which is right.

The line a screen would gain

The job card is a vertical stack: name and status, then function and base model, then run <id> job <id>, then attack and false-trigger rates, then any error (job-list.tsx:126-150). A fourth line inserted after :139 displaces nothing; the card grows downward.

● demo-run completed
x1 & x2 Qwen2.5-7B [lora]
run 20260828-141207 job 481923
adapter /home/<user>/boolback_out/forge/20260828-141207/adapter · epoch 3
ASR 94.2% · FTR 1.1%

The adapter path in that sketch is a shape, not a reading. No real one could be obtained: the cluster API rejected this session's key and forge.listMine requires your identity. The only concrete value anywhere in the repository is the test fixture "/abs/lora" at convex/forge.test.ts:89. A full (non-adapter) build would show model <modelDir> in the same position instead.

Absence and staleness

All four are optional and are absent for every job that has not reached a terminal result, which includes every card on screen while a run is pending or training. adapterPath and modelDir are mutually exclusive by the cluster's own rule, so the line is naturally one or the other and never both. The values are written by the browser, not the server: the card polls the cluster for status and writes what it reads back into Convex (job-list.tsx:71-104), so a card that is never open while a run finishes leaves the fields unset even though the cluster has them.

Cost of deleting

Sixteen lines across four files, all inside tom.quest: convex/schema.ts:190-193, convex/forge.ts:76-79 (result validator) and :96-99 (the patch), app/forge/components/job-list.tsx:94-97 (what the browser sends). The assertions at convex/forge.test.ts:88-90 and :99-100 go with them. app/forge/types.ts:37-41 stays either way — it describes the cluster's response, which keeps carrying these fields. Nothing on the cluster changes.

Recommendation: render adapterPath (or modelDir) and epoch as one line, and delete isAdapter. The reason is that the path is the one fact a finished run leaves behind that the card cannot otherwise tell you — where the weights are — while isAdapter is a restatement of whether that path is present, enforced as such by the cluster.

Two constraints any render has to obey

These come from the interface rules ratified on 2026-08-29 and are stated here so the ruling is made knowing them, not discovered afterwards.

Explanatory prose does not go on a page; a control that needs explaining gets the tap-to-open popover whose body names the backend call. That matters for the pool counters in particular, because staleCancelled and adopted are not self-evident labels. It also means a new value must not be attached with the browser's native title= hover text, which does nothing on a phone. The pool panel currently uses title= in four places (pool-panel.tsx:257, :281, :288, :293); by the same rule those migrate to the popover when that surface is next edited, which a counters render would make it.

Nothing may shift the layout. Every line proposed above sits inside a wrapping row or extends a vertical stack downward, so none of them moves an existing control.

What is left

Four rulings, one per case, each a choice between the recommendation above and its alternative. After them, the changes divide cleanly into two independent pieces of work that touch no common file: the sessions fleet row together with the server-health hook and diagnostic panel, and the pool panel together with the Forge job card.
